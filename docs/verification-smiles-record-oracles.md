## Contract under test

`smiles.record.inspect` explicitly identifies one record and expected revision. The
returned `smiles_record` object has exactly the twelve agreed fields: captured revision
and generation, record ordinal and physical line, five whole-file-relative ranges,
literal atom/bond counts and exact notation. Optional separator/application-data ranges
retain the distinction between absent and present-but-empty. Opaque application data
is neither returned nor decoded. The serialized record object, excluding its parent
state/wire wrappers, must fit 128 KiB. Ordinary state omits the explicit record result;
Debug omits its notation.

The tests use public string commands and the unchanged existing file Open command, not
unreleased Rust API types or a stub. They compare complete Engine state/content and file
bytes before/after query, and verify deferred disclosure from a captured original file
after a new Open and close request without changing that newer session.

## Independent original vectors

The 113-byte multi-record source includes blank/ignored lines, mixed CRLF/LF, nonUTF8/NUL
metadata, an empty application-data suffix and final EOF. Its second meaningful record is:

```text
[13CH2](-[H])[2H].[CH2]7[CH2][CH2]7.[CH2]=[CH2].[CH1]#[CH1]
```

That original 59-byte notation combines isotope13, separate H/deuterium nodes, literal H
counts, an explicit Single branch bond, a cycle, Double/Triple and disconnected components.
Independent literal expectations are ten atoms and seven edges. The file ranges are chosen
from literal byte lengths, not generated by Bondline's parser:

| Record / physical line | Full | Notation | Separator | Application data | Ending |
| --- | --- | --- | --- | --- | --- |
| 2 / 4 | 21..92 | 21..80 | 80..82 | 82..90 | 90..92, CRLF |
| 3 / 6 | 101..108 | 101..106 | 106..107 | 107..107, present empty | 107..108, LF |
| 4 / 7 | 108..113 | 108..113 | absent | absent | 113..113, EOF |

The unchanged external `smiles_file_raw_oracle.py` independently checks these ranges and
exact notation bytes in the actual source file. The unchanged `smiles_oracle.py` consumes
the command's actual returned notation and checks every atom element/isotope/charge/H/
no-implicit marker and every endpoint/order. A wrong first record, a collapsed physical H
and a changed isotope are valid-parser negative controls. Relabeling ring7 to ring1 keeps
the external graph but fails the exact literal record comparison, distinguishing topology
from byte preservation. No Rust reader/writer round trip establishes these expectations.

The maximum notation vector is exactly 65,536 bytes: 4,096 original
`[65535OsH9+15]` tokens, grouped as 1,024 four-atom nested paths, with the first 1,025 Single
edges explicitly spelled. It has 3,072 bonds and branch depth 3. Both the current file parser
and pinned external notation consumer accept it. This is deliberately extreme syntax and
literal metadata; it makes **no chemical plausibility, valence, writer-output or canonical
notation claim**. The same vector has cases with LF and with one MiB of opaque 0xff data
after a TAB. Only its notation/ranges/counts may enter the bounded disclosure object.
Every external maximum-vector atom and endpoint/order is checked; the original source
and metadata remain untouched.

Early fixed-vector exploration used leading-zero isotope spelling. The pinned RDKit
consumer rejects `[013CH2]` and the existing all-zero 65,536-byte isotope-padding vector,
although the source notation profile permits them. The final interoperable vectors above
were selected before the tests were frozen or the command's runtime RED was captured.
Those exploratory consumer refusals are not command failures, a Rust parser defect,
permission to change old consumers or evidence of complete standard conformance.
